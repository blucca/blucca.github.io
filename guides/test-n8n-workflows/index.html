1. Define the records the workflow should return

A useful regression case has a fixture, a workflow export, and an expected business result. Here, the fixture supplies three rows to the Rows input boundary:

[
  { "id": "row-A", "score": 0.9 },
  { "id": "row-B", "score": 0.8 },
  { "id": "distractor", "score": 0.2 }
]

The Select rows Code node keeps scores of at least 0.7 and adds a fresh processedAt timestamp. Its result should contain row-A, then row-B. The third row exercises the filter’s exclusion path.

Write that acceptance rule as an output assertion:

{
  "node": "Select rows",
  "count": 2,
  "pluck": "json.id",
  "equals": ["row-A", "row-B"]
}

count checks how many items arrive. pluck selects the field to compare from each n8n item, starting at json.id. equals checks the ordered values. Order, duplicates, and missing fields all matter.

Choose the fields your release promises to preserve.

Customer IDs, invoice IDs, amounts, and destinations often belong in the contract. This example checks IDs and count; its timestamp can vary on every run. Use full JSON assertions when every output field belongs in the expected result.

The downloadable complete case combines this fixture and assertion. n8n-check imports the prepared export into the real n8n engine, executes it, and compares the captured output.

2. Run the original workflow

Download the two-export Docker demo, extract it into a new folder, and open a terminal there. Start Docker, then run:

sh fixed/run.sh

Expected result: 5/5 checks pass, exit 0. The output contains row-A and row-B.

Setup: Docker with Linux containers and a shell on Linux, macOS, or WSL2. Docker supplies Node and n8n. The first run downloads the official n8n 2.41.7 image and a pinned n8n-check 0.1.6 runner. Workflow execution uses loopback-only networking.

The demo pins those tested versions. The current npm release and GitHub Marketplace Action provide the same count-and-ID assertion format for your own projects.

3. Catch the same-size, wrong-ID result

From the same extracted folder, run the deliberately changed export:

sh wrong-id/run.sh

Expected result: 4/5 checks pass, exit 1. The changed Code node assigns "wrong-row" to both selected rows. n8n still finishes successfully. The count remains two. The exact-ID check identifies the changed business result.

Open the wrong-ID report.json. The failed check includes this comparison:

{
  "name": "Select rows: output 0 pluck json.id",
  "passed": false,
  "expected": ["row-A", "row-B"],
  "actual": ["wrong-row", "wrong-row"]
}

junit.xml carries the result into CI reporting. Exit 1 is the intended outcome for this negative control. Exit 2 identifies a setup error; the terminal output gives the next diagnostic.

What do the five checks cover?

Engine completion, item count, ordered IDs, and two mock-transport checks. This example sends zero HTTP requests. The recorded checks include each expected and actual value; the completed Docker-pack CI run exercises both folders.

4. Create a case for your own n8n export

Start with one result your next release must preserve, such as which invoice IDs reach the accounting step.

  1. Open the local case builder and import your workflow export.
  2. Choose the fixture input boundary and the downstream output node. For a Sheets → Code → Slack workflow, use fixture rows in place of Sheets and select stop after Code to check that transformation.
  3. Select Selected field + item count. Enter a field such as json.invoiceId, then set the exact expected IDs and count.
  4. Review any inputs and expectations prefilled from exported pins against your business rule. Include a relevant row and an excluded row so the filter gets exercised.
  5. Download the local run pack and run sh run.sh, or download the GitHub Actions file for CI.

Imported workflow contents stay in the browser tab. The runner supports JSON fixtures, self-contained workflow slices, and controlled HTTP responses. Live trigger delivery and provider behavior belong to the integration checks around that slice.

Commit the case alongside the export. When the workflow changes, rerun the same inputs and expected result. A deliberate wrong-ID control gives you a concrete example of the failure the assertion is designed to catch.
