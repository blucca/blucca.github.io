Your workflow. Three steps.

  1. Export and define the contract. Open the local case builder. Choose the input boundary, add synthetic items and HTTP responses, and set the outputs or request bodies the workflow should preserve. Download workflow.json and the completed case.json.
  2. Choose the deployed and candidate releases. Add the files to your repository. Get the complete upgrade YAML, save it as .github/workflows/n8n-upgrade.yml, and set its two versions and file paths.
  3. Read both results before rollout. Commit, then open GitHub Actions. Each engine gets its own job, summary, and JSON/JUnit artifacts. A failed expectation makes that job fail while the other version continues.

A failing deployed baseline identifies behavior to address today. A candidate mismatch shows what needs review before the upgrade. Keep the expectation tied to the result your client needs.

One case. Two pinned runtimes.

The key configuration inside the job:

strategy:
  fail-fast: false
  matrix:
    n8n: ['2.38.4', '2.41.7']
steps:
  - uses: actions/checkout@v4
  - uses: blucca/n8n-check@v0.1.4
    with:
      n8n-version: ${{ matrix.n8n }}
      workflow: workflow.json
      case: case.json
      out: results/contract
