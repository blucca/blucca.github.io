Freeze the tool’s JSON result.

A tool returns a dictionary containing invoice-42. A later tool appends invoice-43 to the application’s shared list. In the recorded Pydantic AI 2.68.0 stock run, the first tool’s earlier history acquires both IDs. All agents still finish with done.

For this ordinary JSON return, give the tool its own snapshot:

from copy import deepcopy

@agent.tool_plain
def read_orders() -> dict[str, list[str]]:
    return deepcopy(state)

The lab checks the first result afresh in both subsequent FunctionModel requests, then independently decodes all_messages_json() after completion.

Measured scope: a JSON mapping with a nested list and two sequential tools. The application state reaches both IDs in every run. The separate helper-interception control lives in the lab; the snippet above uses the ordinary tool API.

Finish fetching before reporting the SQL result.

execute() returns successfully. The first row is real. Fetching the remaining rows then raises sqlite3.OperationalError. In Agno 3.2.0, the public SQL tool returns the string "[]" for this failure.

The existing fix by adityav1709 in PR #11680 lets fetch exceptions reach the outer run_sql_query error handler. This excerpt from its run_sql keeps successful transaction completion and row collection together:

with self.Session() as sess, sess.begin():
    result = sess.execute(text(sql))

    if not result.returns_rows:  # type: ignore[attr-defined]
        return []

    if limit is None:
        rows = result.fetchall()
    elif limit > 0:
        rows = result.fetchmany(limit)
    else:
        rows = []
    return [row._asdict() for row in rows]

The outer handler reports Error running query: …. A legitimate empty SELECT still returns "[]"; non-returning CREATE and INSERT complete normally. An independent DBAPI connection confirms the inserted value 7.

Use a failure that happens during fetching. This lab’s SQLite UDF raises on the third row: execute → first row → fetch error. SQLAlchemy result methods stay unchanged. Both unlimited and limit-2 tool queries hit the real error.

Measured scope: file-backed SQLite, SQLAlchemy 2.0.57, published Agno 3.2.0 and two frozen SQL modules. The package compares stock/main with the existing PR’s module; that patch was closed and unmerged at discovery. Production drivers and their error contracts get their own tests.

Save from the result of this call.

A purchasing agent receives the correct total 50, while its original end-hook CSV row has empty quantity and unit-price columns. In OpenAI Agents 0.24.0, the nested result still carries the structured purchase and its call ID.

Save in the public custom_output_extractor. The lab’s callback validates this call’s input, appends its complete row, then returns the original output to the parent:

async def extract(result):
    purchase = Purchase.model_validate(result.context_wrapper.tool_input)
    invocation = result.agent_tool_invocation
    assert invocation is not None
    call_id = invocation.tool_call_id
    assert result.final_output == expected_outputs[call_id]
    row = [call_id, purchase.quantity, purchase.unit_price, result.final_output]
    observed.append(row)
    if save_with_extractor:
        append_row(row)
    return result.final_output

Excerpt from the complete fixture app: expected_outputs is its acceptance oracle and save_with_extractor selects the recorded control. Register with calculator.as_tool(parameters=Purchase, custom_output_extractor=extract, …); the full lab supplies the schema, models, parent and CSV initialization. It initializes the header once and appends each complete row synchronously, without an intervening await.

Read the saved CSV back. Check the header, row count, input fields and call IDs. The two-call control makes B finish first: B / 3 / 7 / 21, then A / 2 / 25 / 50. The parent receives A: "50" and B: "21" and completes normally.

Measured scope: completed, non-streaming calls, structured integer purchases, one event loop and a local CSV. ScriptedModel derives totals from the actual nested input. Shared application context keeps its normal SDK semantics; approval/resume and distributed write recovery use separate contracts.
