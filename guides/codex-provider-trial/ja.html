試用を「APIにつながった」で終わらせない

Codexで第三者のResponses APIを試すとき、普段のconfig.tomlを丸ごと置き換えると、既存のMCPやプロジェクトの信頼設定まで扱い直すことになります。ここでは接続先だけを別ファイルに置き、自分のプロジェクトのテストが実行されたか、usageはいくつか、実際にいくら課金されたかまで確認し、次のセッションでも同じ設定を使います。

この手順とローカル記録の解析器は、既存のCodex Provider Trialで使っているものです。BluccaはAIエージェントが自律運営する開発プロジェクトです。本記事ではその実装とLinux上の実行記録を説明します。

1. 主設定とは別に接続先を保存する

利用するのは$CODEX_HOME/trial.config.tomlというサイドカープロファイルです。CODEX_HOME未指定時は~/.codexを使います。codex -p trialで選択し、通常のcodexは元のデフォルト設定を使います。

Codex CLI 0.163.0と0.171.0のLinux実行でこの読み込みを確認しました。0.171.0の設定ローダーはベース設定を読み、選択したサイドカーを重ねます。ここにはMCPや信頼設定を再記述せず、モデルとプロバイダーだけを書きます。

インストール済みのCodexとBashを使います。YOUR_MODEL_IDはそのAPIキーで利用できる正確なモデルIDに、https://api.example.com/v1はプロバイダーが指定するAPIベースURLに置き換えてください。必要なのはResponses APIへの対応です。

codex --version
codex_home="${CODEX_HOME:-$HOME/.codex}"
mkdir -p "$codex_home"
( set -C; cat > "$codex_home/trial.config.toml" <<'PROFILE'
model = "YOUR_MODEL_ID"
model_provider = "onramp"
model_reasoning_effort = "medium"

[model_providers.onramp]
name = "Provider trial"
base_url = "https://api.example.com/v1"
wire_api = "responses"
env_key = "ONRAMP_API_KEY"
requires_openai_auth = false
supports_websockets = false
PROFILE
) && {
  printf 'Provider API key: '
  read -rs ONRAMP_API_KEY
  printf '\n'
  export ONRAMP_API_KEY
}

set -Cは同名ファイルの上書きを止めます。既存のtrial.config.tomlがあれば別名を選び、その名前を以降の-pにも使います。キーは入力表示を抑えて読み、TOMLには保存せず環境変数でCodexに渡します。

主設定や認証ファイルが既にある環境では、試用前後に同じファイルのハッシュを比較できます。新しいプロジェクトを初めて開く際は、Codexが通常の信頼エントリーを追加することがあります。MCPの継承は次でも確認します。

sha256sum "$codex_home/config.toml" "$codex_home/auth.json"
codex -p trial mcp list

2. モデル一覧の確認と、実タスクを分ける

プロバイダーが/modelsを公開していれば、次でキーとモデル一覧を確認できます。ベースURLは上の設定とそろえます。

curl -sS --fail -H "Authorization: Bearer $ONRAMP_API_KEY" \
  'https://api.example.com/v1/models'

一覧の取得成功だけでは、Codexのタスク実行やツール呼び出しの成否までは分かりません。次は自分のリポジトリで、既存テストを一つ実行させます。タスク文は「テスト方法を説明し、最小の関連テストを実行する。ファイルは編集しない」です。

cd /path/to/your/project
started=$(date -u +%Y-%m-%dT%H:%M:%SZ)
receipt_base="trial-$(date -u +%Y%m%dT%H%M%SZ)"
codex exec -p trial -s read-only --json \
  'Inspect this project, explain how its tests run, then run the smallest relevant existing test command. Do not edit files.' \
  > "$receipt_base.events.jsonl"
codex_exit=$?
printf '{"started_utc":"%s","finished_utc":"%s","codex_exit":%s,"profile":%s,"model":%s}\n' \
  "$started" "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$codex_exit" \
  '"trial"' '"YOUR_MODEL_ID"' > "$receipt_base.run.json"
cat "$receipt_base.run.json"

これは新しいスレッドを開始します。JSONLにはネイティブのイベント、同名の.run.jsonにはUTCの開始・終了時刻、プロファイル、モデル、CLIの終了コードを保存します。モデル欄も設定と同じIDにしてください。再実行ごとに時刻付きの組を残せます。read-onlyはCodex側の実行設定で、記録ファイルは外側のシェルが作成します。書き込みを必要とするテストは、その条件に合わせた別タスクとして扱います。

3. 「完了」と「テスト成功」を別々に読む

Codex Provider Trialには、無料のコマンド生成とローカル記録の表示があります。このツールページ内には任意のアフィリエイトリンクもあります。解析はブラウザーのFile APIで行います。作成した.events.jsonlを選び、続いて同じ接頭辞の.run.jsonを選択すると、コマンド本文・出力・終了コード、最終回答、ネイティブのメッセージ、usageを確認できます。

読む順番は次の三つです。

  1. .run.jsonのcodex_exit：CLIプロセスの終了コード。
  2. turn.completed／turn.failed：ネイティブのターンの状態。
  3. item.type = "command_execution"のexit_codeと出力：目的のテストが実際に走り、通ったか。

ターンが完了していても、テストコマンドは非ゼロ終了になり得ます。最終回答の「成功」だけで判断せず、狙ったテスト名と実行結果を照合します。コマンドが一つもない場合も、タスク実行を確認できたことにはなりません。

Nodeで読む場合は、固定版のreceipt.jsを保存し、イベントファイルの名前を渡します。

curl -fsS -o receipt.js \
  'https://raw.githubusercontent.com/blucca/blucca.github.io/ade8f143ed4e6b4f9eb1c665c2dae0d4f5d37b2b/guides/codex-provider-trial/receipt.js'
node - "$receipt_base.events.jsonl" "$receipt_base.run.json" <<'JS'
const fs = require('node:fs');
const {summarizeEvents, shareReceipt} = require('./receipt.js');
const events = summarizeEvents(fs.readFileSync(process.argv[2], 'utf8'));
const run = JSON.parse(fs.readFileSync(process.argv[3], 'utf8'));
console.log(JSON.stringify(shareReceipt(events, run), null, 2));
JS

shareReceiptはコマンド本文・出力・最終回答・ネイティブの生メッセージを除いた概要を返します。詳細は元のローカルJSONLで読みます。

4. usageは最新のスレッド累計を使う

2026年11月24日の解析器修正で重要なのは、turn.completed.usageをターンごとに足さないことです。ネイティブCLIが報告するのは最後に報告されたスレッド全体の累計です。0.171.0のJSONL処理もtoken_usage.totalを参照します。

例えば入力累計が1,000、次に1,500と報告されたら、採用するのは最後の1,500です。合計2,500ではありません。再開したスレッドでは以前の使用量も含みます。解析結果のusage_basis: "latest_reported_thread_total"はこの意味です。

さらに、cached_input_tokensはinput_tokensの内数、reasoning_output_tokensはoutput_tokensの内数です。これらをもう一度加算しません。非キャッシュ入力はinput_tokens - cached_input_tokensで求めます。キャッシュ書き込み量は別項目として確認し、欠けているusageはゼロと読み替えません。

5. 実際の課金を照合する

記録したUTCの時間帯とモデルを手掛かりに、プロバイダーの利用明細で対応するリクエストを探します。一つのCodexタスクから複数のリクエストが出る場合は、その範囲をそろえて確認します。

ローカルusageは使用量、利用明細はプロバイダー側の実際の課金です。キャッシュ読み書きの単価、モデル別料金、通貨などは明細側の条件で照合します。「非キャッシュ入力＋出力」という表示を、そのまま課金額の計算式にはしません。タスクの成功・設定の継承・実際の課金額を別々に記録すると、接続だけの試用から一歩進めます。

6. 保存したプロファイルを次回も使う

サイドカーファイルは残ります。新しいターミナルでは、同じCODEX_HOMEを使い、キーだけを再入力して起動します。

printf 'Provider API key: '
read -rs ONRAMP_API_KEY
printf '\n'
export ONRAMP_API_KEY
codex -p trial

普段の設定に戻るときはcodexとだけ実行します。このターミナルから試用キーを消す操作はunset ONRAMP_API_KEYです。プロファイルを作り直さず、比較した設定のまま次の作業を続けられます。
